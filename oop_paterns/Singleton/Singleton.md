
# Singleton

Гарантирует, что у класса есть только один экземпляр, и предоставляет к нему глобальную точку доступа. В современном C++ (начиная с C++11) «ленивая» и потокобезопасная инициализация делается через статический локальный переменный объект (Magic Statics).

```c++
class Singleton {
public:
    static Singleton& getInstance() {
        static Singleton instance; // Создается один раз потокобезопасно
        return instance;
    }
    
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;

private:
    Singleton() = default;
    ~Singleton() = default;
};
```


## 🛠️ [Как правильно написать Singleton на современном C++](Singleton.cpp)

В C++11 и новее идеальный Singleton пишется всего в несколько строк благодаря концепции Magic Statics (статические локальные переменные). Стандарт языка гарантирует, что такая переменная инициализируется потокобезопасно при первом вызове функции.


## ⚠️ Почему Singleton часто называют «Антипаттерном»?

Несмотря на простоту, в реальном продакшене Singleton часто порождает огромные проблемы с архитектурой. Вот три главные причины, почему его стоит избегать:
1. **Глобальное состояние (Global State)**: Singleton — это, по сути, замаскированная глобальная переменная. Если любой модуль программы может в любой момент изменить состояние Singleton, код становится непредсказуемым. Баг в одном месте может сломать логику на другом конце приложения.
2. **Скрытые зависимости**: Когда метод класса использует DatabaseConfig::getInstance(), эта зависимость скрыта внутри тела метода. Глядя на сигнатуру функции, вы не понимаете, что ей для работы нужна база данных.
3. **Невозможность модульного тестирования (Unit Testing**): Это самая большая боль. Из-за того, что экземпляр один и он глобальный, вы не можете изолировать тестируемый класс. Вы не можете «подменить» реальную базу данных на фальшивую (Mock-объект), чтобы быстро прогнать тесты без реального подключения к сети.


## 🚀 [Альтернатива: Внедрение зависимостей (Dependency Injection)](Singleton_alternative.cpp)

Вместо того чтобы класс сам лез за Singleton, правильнее передать ему нужный объект через конструктор (желательно по ссылке или через умный указатель).

**Почему это лучше:**
• Нет скрытых связей. Сразу видно: UserManager не может работать без IDatabase.
• В тестах вы сможете легко создать class MockDatabase : public IDatabase и передать её в UserManager, не трогая настоящую БД.
